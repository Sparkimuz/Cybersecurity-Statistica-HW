Core Conceptual Distinctions

Key definitions required by the specification

1. Key Generation vs. Key Derivation

Key Generation creates brand-new true randomness (entropy) from a physical/OS random number generator—it happens only once when creating the wallet.
Key Derivation (BIP-32/39/44) deterministically computes child keys from the master seed using hash functions (HMAC-SHA512). Given the same seed, you always recover the exact same keys.

2. Public-Key Cryptography vs. Hashing

Public-Key Crypto (secp256k1) is a one-way trapdoor function ($Q = kG$) that preserves algebraic structure, allowing private keys to sign transactions (ECDSA) and public keys to verify them.
Hashing (Keccak-256) compresses data of any size into a fixed-length digest while destroying all algebraic structure (Avalanche Effect).

3. Checksums vs. Encoding

Encoding simply translates data into a different alphabet for readability (e.g., bits to 12 English words in BIP-39, or bytes to Hexadecimal 0x...) with zero security or error checking.
Checksums (EIP-55, BIP-39 last word) embed redundant hash bits to detect human typing mistakes before funds are lost.

4. SHA-2 / SHA-512 vs. Keccak / SHA-3

SHA-2 (SHA-256 / SHA-512) uses the classic Merkle–Damgård construction (used in Bitcoin and inside BIP-32/39).
Keccak / SHA-3 uses a modern Sponge construction (absorbing and squeezing bits in a 1600-bit state) that is immune to length-extension attacks. Ethereum uses original Keccak-256 rather than final NIST SHA3-256 because Ethereum launched before NIST changed the padding constant.

Chronological Context

1977 — RSA
First practical public-key cryptography system (based on prime factorization). Later replaced in blockchains by smaller, faster Elliptic Curve Cryptography.
2001 — SHA-2 / SHA-512
Standardized by NIST. Used in wallets for BIP-39 checksums (SHA-256) and seed/key derivation (HMAC-SHA512).
2012 — BIP-32
Introduced Hierarchical Deterministic (HD) wallets, allowing one root seed to generate an entire tree of keys.
2013 — BIP-39
Standardized 12–24 word mnemonic phrases and PBKDF2 seed generation for human-friendly backups.
2014 — BIP-44
Defined standard multi-account, multi-coin derivation paths (e.g., m/44'/60'/0'/0/0 for Ethereum).
2015 — SHA-3 (NIST)
NIST standardized SHA-3 based on Keccak. Ethereum adopted the original Keccak-256 variant.
2016 — EIP-55
Vitalik Buterin introduced backward-compatible mixed-case checksums for Ethereum addresses.

Why Use Multiple Primitives?

A wallet pipeline cannot use a single algorithm for everything because each stage solves a fundamentally different problem:

BIP-39 / BIP-32 / BIP-44 → Key Management & Derivation Humans cannot memorize random 256-bit hex strings. BIP-39 provides a readable backup and slows down brute-force attacks (PBKDF2), while BIP-32/44 derive isolated accounts from one backup.
secp256k1 → Public/Private Keys & Digital Signatures Authorizing transactions requires an asymmetric mathematical link ($Q = kG$) so anyone can verify an ECDSA signature using the public key without ever seeing the private key.
Keccak-256 → One-Way Hashing & Compression Hashing destroys the algebraic structure of the elliptic curve public key (adding an extra security layer) and shortens the 64-byte public key into a compact 20-byte address.
EIP-55 → Checksum & Error Detection Raw hex addresses have no redundancy: a single mistyped character sends funds to a valid but unowned address forever. EIP-55 uses capitalization to catch 99.997% of typos.
